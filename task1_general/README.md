## 1. 建立預測模型時偏好用什麼語言?為什麼?

Python。

另外它公開的套件很多,資料處理、機器學習、深度學習、畫圖都有現成的可以用,不用自己從頭寫。用的人也多,遇到問題通常找得到別人的討論或範例,跟同事交接程式也比較沒有門檻。

## 2. 請舉一個用 SQL 擷取資料的例子

我做過一套給牙科醫師用的臨床照片對齊系統。系統會自動算出每張照片要轉幾度才會擺正,醫師覺得不對可以自己手動調整。有一次要改演算法,改之前我想先知道現在的版本準不準,所以要把「醫師有手動調整過的照片」撈出來,比較系統算的角度和醫師調的角度差多少。

資料存在三張表裡(這裡把欄位簡化過):

`patients`,一位病人一筆

| 欄位 | 說明 |
|---|---|
| patient_id | 病人編號(主鍵) |
| created_at | 建檔日期 |

`visits`,一次回診一筆

| 欄位 | 說明 |
|---|---|
| visit_id | 回診編號(主鍵) |
| patient_id | 是哪位病人的回診,對應 patients.patient_id |
| visit_date | 回診日期 |

`photos`,一張照片一筆

| 欄位 | 說明 |
|---|---|
| photo_id | 照片編號(主鍵) |
| visit_id | 是哪一次回診拍的,對應 visits.visit_id |
| view_type | 拍攝的角度(正面、側面等) |
| auto_angle | 系統算出來的旋轉角度 |
| manual_angle | 醫師手動調整後的角度,沒調過就是空的 |

三張表的關係是:一位病人有很多次回診,一次回診有很多張照片。所以要知道某張照片是哪位病人、哪一天拍的,就要用 `visit_id` 從 photos 接到 visits,再用 `patient_id` 從 visits 接到 patients。

```sql
SELECT p.patient_id,
       v.visit_date,
       ph.view_type,
       ph.auto_angle,
       ph.manual_angle
FROM photos ph
JOIN visits v   ON v.visit_id = ph.visit_id
JOIN patients p ON p.patient_id = v.patient_id
WHERE ph.manual_angle IS NOT NULL
ORDER BY p.patient_id, v.visit_date;
```

這段的意思是:從照片表出發,接上回診和病人,只留下醫師有調整過的照片(`manual_angle` 不是空的),再依病人和日期排好。撈出來之後,每一筆就有系統的角度和醫師的角度可以直接相減。

只留醫師調過的照片是有原因的。沒調過的照片沒有醫師的答案可以比,如果把它們當成「系統算對了」一起算進去,準確率會被灌水。

## 3. 請舉一個跟同事對做法意見不同的例子,你怎麼處理?

我遇到意見不同的時候,最常見的狀況是大家會先守著自己的想法。所以我習慣的做法是先把我的看法和理由講清楚,然後換對方講,聽他是怎麼想的,最後再一起評估哪個方向比較合適。

舉一個例子。同事做了一套產房護理人員口述紀錄的語音辨識,遇到嬰兒哭聲的時候辨識會變差,他的想法是在辨識前面加一個聲音分離的模型,先把哭聲去掉。

我先講了我的看法:我擔心這類模型在分離聲音的時候,會連講話的部分一起改到,而臨床紀錄裡如果數字辨識錯,比留一點哭聲還嚴重。接著我聽他的想法,他的出發點也很合理,哭聲確實是辨識變差的主因,把它去掉是最直接的做法。

兩邊都有道理,光用講的分不出來,所以我們先講好怎樣才算有改善:每一個音檔處理後的辨識結果都不能比原本差。然後我寫了評估的程式,把 14 種前處理的做法都跑過一遍。結果沒有一種能完全符合,最好的那一種平均錯誤率有降(4.8% 降到 4.3%),但還是有幾個音檔變差。

看到結果之後就不用再爭了,我們決定維持用原始音檔辨識,改成在辨識出來的文字上面想辦法。

## 4. 你最大的優點和缺點是什麼?對這份工作會有什麼影響?

優點是我會習慣先設想下一步。

舉個例子,之前單位在發展 LLM 應用的時候,大家多半是直接呼叫 API 來試驗某個應用可不可行。我在做的時候就先想到,主管之後應該會需要一個有畫面、可以自己操作的版本,所以雖然當時沒有人要求,我還是先把操作介面設計出來。後來主管果然提到這個需求,我就可以直接把已經做好的東西拿出來。這種時候我自己會很有成就感。

這個習慣也有壞處,萬一我猜錯主管要的方向,那段時間就等於白花了。不過對我來說這個過程是一種磨練,猜過幾次之後會越來越了解每個人的思路,後面溝通起來也比較順。

缺點是我習慣一次做太多事情,同時進行的項目一多,切來切去效率就會變差。我現在的做法是每件事都留一份簡單的紀錄,寫目前做到哪、下一步是什麼,然後跟主管確認優先順序,先把最重要的做完。

對這份工作的影響,我想是我會主動多想一步、提早準備,但也需要主管幫我一起確認方向和優先順序,避免我想太遠或同時攤開太多事。
