## 1. 建立預測模型時偏好用什麼語言?為什麼?

Python。

最主要的原因是從看資料、訓練到部署都可以用同一種語言做完。我平常用 pandas 看資料,scikit-learn、LightGBM、PyTorch 訓練,訓練完可以直接包成服務,或轉成 ONNX 放到邊緣裝置上,中間不用重寫。這份作業的 Task 2 和 Task 3 也是這樣,各一支 `main.py` 從讀資料跑到出圖。

另外新的方法通常最先有 Python 的實作,要驗證或修改都方便。我合作的對象有醫師、工程師、學生,Python 是大家最容易看懂、也最容易自己跑起來的。

資料在資料庫裡的時候我會先用 SQL 把需要的部分篩好再拉出來,不會整包丟進 pandas。Python 跑太慢的地方就改成向量化的寫法,或把那一段交給 ONNX Runtime 之類的處理。

## 2. 請舉一個用 SQL 擷取資料的例子

我做過一套給牙科醫師用的臨床照片對齊系統,病人、回診、照片都存在資料庫裡。有一次要改對齊的演算法,改之前我想先知道現在的版本到底準不準,標準是醫師自己手動修正過的結果。

所以我用 SQL 把這份評估資料撈出來:照片 join 回診和病人,只留醫師手動修正過的,排除已刪除的,然後把系統算的角度和醫師改的角度放在一起比。下面的表和欄位名稱有簡化過。

```sql
SELECT p.id AS patient_id, v.visit_date, ph.view_type,
       ph.auto_angle, ph.manual_angle
FROM photos ph
JOIN visits v ON v.id = ph.visit_id
JOIN patients p ON p.id = v.patient_id
WHERE ph.manually_corrected = 1
  AND ph.deleted_at IS NULL
ORDER BY p.id, v.visit_date;
```

這裡比較需要注意的是篩選條件。醫師沒動過的照片不能拿來算,因為那些照片的「答案」就是系統自己算的,拿來評分一定全對。實際量完之後,有幾個我原本覺得一定會變好的改法,結果反而比現在的版本差,就沒有上線。

## 3. 請舉一個跟同事對做法意見不同的例子,你怎麼處理?

同事做了一套產房護理人員口述紀錄的語音辨識,遇到嬰兒哭聲的時候辨識會變差。當時的想法是在辨識前面加一個聲音分離的模型,先把哭聲去掉。

我對這個做法有疑慮。這類模型是用生成的方式把聲音分開,有可能連講話的部分一起改掉,而臨床紀錄裡如果數字辨識錯,比留一點哭聲嚴重得多。

我沒有直接反對,而是先跟同事討論「怎樣才算有改善」。後來我們講好的標準是:每一個音檔處理後的辨識結果都不能比原本差。接著我寫了評估的程式,把 14 種前處理的做法都跑過一遍。結果沒有一種能完全符合,最好的那一種平均錯誤率有降(4.8% 降到 4.3%),但還是有幾個音檔變差。

有了這些數字就不用再爭了。最後我們決定維持用原始音檔辨識,改成在辨識出來的文字上面想辦法。

這件事之後,我遇到意見不同的情況,都會先確認大家是不是在用同一個標準看這件事,通常問題就出在這裡。

## 4. 你最大的優點和缺點是什麼?對這份工作會有什麼影響?

優點的話,我覺得是做事習慣先量測再下結論。我會留一個什麼都不做的 baseline,也會把結果不如預期的部分講出來。像 Task 2 我自己做的特徵沒有比較好,我就直接拿掉並寫在說明裡。

另一個是我做過從頭到尾的流程,包含資料標註、訓練、寫論文(2024 年在 Biomedical Journal 發表髖關節超音波自動判讀的研究,共同第一作者),到把模型部署到醫院的 AI 平台。我大部分的專案都是跟醫師一起做,所以也習慣跟不同背景的人溝通需求。

缺點是我容易同時接太多事情,切來切去效率會變差。我現在的做法是每個專案都寫一份簡單的紀錄,記目前做到哪、下一步是什麼,然後跟主管或合作的人確認優先順序。

另外我有時候會把一個結果做得比實際需要的還仔細,花掉太多時間。現在我會先問清楚這個分析是要拿來做什麼決定,做到夠用就停。
